# Gameplay Flow & State Model

This document defines the gameplay lifecycle, state model, and action rules for
human and optional bot players using the existing `backend/src/game` engine.

## Core Concepts
- **Table**: A persistent room (`game_tables`) where players sit and play.
- **Seat**: A position at a table (`table_seats`), can be empty or occupied.
- **Hand**: A single round of poker from blinds to showdown.
- **Engine**: In-memory state machine per table (`PokerEngine` + `GameStateMachine`).

## Hand Lifecycle (Texas Hold'em)
1. **PRE_GAME**
   - Dealer/button position determined.
   - Blinds posted.
   - Deck shuffled.
2. **PRE_FLOP**
   - Hole cards dealt.
   - Action starts left of big blind.
3. **FLOP**
   - Burn + 3 community cards dealt.
   - Action starts left of dealer.
4. **TURN**
   - Burn + 1 community card dealt.
   - Action starts left of dealer.
5. **RIVER**
   - Burn + 1 community card dealt.
   - Action starts left of dealer.
6. **SHOWDOWN**
   - Hands evaluated.
   - Pot(s) distributed.
7. **HAND_COMPLETE**
   - Results stored.
   - Next hand setup.

## Turn Order
- **Pre-flop**: starts left of the big blind.
- **Post-flop**: starts left of the dealer/button.
- Actions rotate among active (non-folded) players.

## Player States
- **Active**: seated and not folded.
- **Folded**: removed from the current hand.
- **All-in**: no chips left; still eligible for pots.

## Action Rules (Simplified)
- **CHECK**: only if `currentBet == 0`.
- **CALL**: match `currentBet` or go all-in if short.
- **RAISE**: must be greater than `currentBet`.
- **FOLD**: always allowed.
- **ALL_IN**: allowed with any remaining stack.

## State Model (Server)
The in-memory engine tracks:
- `state` (street)
- `pot`, `sidePots`, `currentBet`
- `communityCards`
- `players` (id, seat, stack, folded)
- `actions` (history for the hand)

The database stores:
- `game_tables` (table metadata)
- `table_seats` (who sits where)
- `games` (hand metadata)
- `hand_history`, `player_cards`, `community_cards`, `game_results`, `rng_audit`

## Bot Interaction
- Bots only act **after a human action**.
- Bot actions are generated by `botStrategy` and applied through the same engine.
- Bots are limited to **5 per table**.

## API Contract (Planned)
- `POST /api/v1/tables/:tableId/action`
  - Request: `{ action, amount }`
  - Response: `{ success, state, botActions }`
- `GET /api/v1/tables/:tableId/state` (optional)
  - Response: current game state snapshot.

## UI Expectations
- Live state updates per action (human + bot).
- Visible turn indicator and allowed actions only.
- Pot size, blinds, and community cards always visible.
